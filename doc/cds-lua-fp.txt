                                                                    *cds-lua-fp*
cds-lua-fp provides reusable list operations and error propagation for Lua
5.1 and later, including LuaJIT and Neovim. It has no dependencies outside
the Lua standard library.

Use |cds.fp| to express transformations such as selecting records, extracting
fields, and removing duplicates without writing a loop for each operation.
Use |cds.result| to chain operations that return `value` or `nil, err` and
handle the first failure in one place. For plugins that share the library,
|cds.needs| checks required APIs at startup, and |cds.module| makes calls to
missing APIs report the module and name involved.

Install with `luarocks install cds-lua-fp`, or add
`{ "cds-io/cds-lua-fp", lazy = true }` to a lazy.nvim configuration.
The Neovim library cds-lua also declares it as a dependency.
  Lists ............................................................. |cds.fp|
  The Result convention ......................................... |cds.result|
  Names a module does not have .................................. |cds.module|
  Taking the library ............................................. |cds.needs|

                                                                        *cds.fp*
Use these helpers when a loop's purpose is a standard list operation:
selecting, transforming, searching, or accumulating. Naming the operation
lets the callback focus on the application rule. They work in plain Lua
as well as Neovim.

For example, select enabled jobs and extract their names: >lua

  local fp = require("cds.fp")
  local jobs = {
    { name = "build", enabled = true },
    { name = "deploy", enabled = false },
  }
  local enabled = fp.filter(jobs, function(job) return job.enabled end)
  local names = fp.map(enabled, function(job) return job.name end)
  assert(#names == 1 and names[1] == "build")
  assert(#jobs == 2) -- the input list is unchanged
<
Inputs are dense sequences indexed from 1: traversal uses `ipairs`, which
stops at the first missing index. Helpers do not mutate the input list;
returned records are the original objects, not deep copies. Callbacks may
still mutate those objects, so keep them pure when sharing input data.

Use `map` when every input produces a value, `filter_map` when some inputs
should be omitted, and |cds.result.traverse()| when a failed conversion
should reject the whole list. Callback arguments come last so multiline
functions sit directly below the operation they define.

------------------------------------------------------------------------------
                                                                  *cds.fp.map()*
                             `fp.map`({list}, {fn})
Transform every item while retaining its position. Use this to extract a
field or convert a list to another representation. A nil callback result
raises an error identifying the item: silently creating a hole would make
later `ipairs` loops stop early. False is a valid result.

>lua
  local fp = require("cds.fp")
  local names = fp.map({ { name = "Ada" }, { name = "Lin" } }, function(user)
    return user.name
  end)
  assert(table.concat(names, ", ") == "Ada, Lin")

Remembers one answer per slot, kept while the slot's key still matches.
The slot is the first argument unless `slot` says otherwise (a table slot
is held weakly, so the memo follows the object's life); the key is nil
unless `key` says otherwise, so a slot alone decides. A failure (a nil
first value) is never remembered, and `keep` refuses any other answer
that should not be. Every value the function returned comes back. The
second value returned is the memo: `held(...)` says whether the slot's
answer is in, `forget()` drops them all.

>lua
  local fp = require("cds.fp")
  local parsed = fp.memoize(function(path) return read(path) end, {
    key = function(path) return mtime(path) end,
  })
  parsed("a.txt")   -- reads
  parsed("a.txt")   -- the answer, while a.txt's mtime is the same
<
Class ~
{cds.fp.MemoizeOptions}
Fields ~
{slot} `(optional)` `(fun(...): any)` the slot the arguments name; the first argument unless given
{key} `(optional)` `(fun(...): any)` what the slot's answer stays valid under; nil unless given
{keep} `(optional)` `(fun(...): boolean)` whether an answer (every value returned) is worth remembering

                                                                    *cds.result*
Use `result` when several operations can fail and later operations need the
previous result. It carries the first error past the remaining steps, so
you can handle failure once instead of repeating a check after every call.
It uses ordinary Lua return values: `value` for success, `nil, err` for
failure. There is no Result object to construct or unwrap.

For example, parse a setting, validate it, then format it for display: >lua

  local result = require("cds.result")
  local function parse(text)
    local n = tonumber(text)
    if n == nil then return nil, "expected a number" end
    return n
  end
  local function positive(n)
    if n <= 0 then return nil, "must be positive" end
    return n
  end
  local function label(text)
    local value, err = parse(text)
    value, err = result.bind(value, err, positive)
    return result.map(value, err, function(n)
      return "Retries: " .. n
    end)
  end

  assert(label("3") == "Retries: 3")
  local value, err = label("oops")
  assert(value == nil and err == "expected a number")
  -- Neither positive nor the formatting callback runs on this failure.
<
Choose `bind` for a callback that can return `nil, err`; choose `map` for
one that produces a non-nil value. Use `traverse` to validate or transform
a whole list when any failed item should reject the result. For a list
transformation with no error propagation, use |cds.fp.map()|.

Only nil signals failure: false and zero are successful values. These
helpers do not catch thrown errors; callbacks must return expected failures
as `nil, err`. The caller decides whether to display, log, or return the
final error.

Keep both return values in locals before passing them to `bind` or `map`.
Lua keeps only the first return value of a call followed by more arguments:
`result.bind(parse(text), nil, positive)` would discard the parse error.

------------------------------------------------------------------------------
                                                             *cds.result.bind()*
                      `result.bind`({value}, {err}, {fn})
Run the next fallible step only if the previous step succeeded. On failure,
return `nil, err` unchanged without calling `fn`; on success, return what
`fn(value)` returns. This prevents later steps from acting on missing data.

>lua
  local result = require("cds.result")
  local called = false
  local value, err = result.bind(nil, "file not found", function(text)
    called = true
    return text:upper()
  end)
  assert(value == nil and err == "file not found" and not called)
<

{value} `(T?)`
{err} `(any)`
{fn} `(fun(value: T): U?, any)`
Return ~

`(any)` err

------------------------------------------------------------------------------
                                                                *cds.result.map*
                                  `result.map`
Transform a successful value while preserving an earlier failure. Use this
name when the callback has no expected failure case, such as formatting a
validated number. It is an alias of `bind`: this distinction documents the
callback's intent, and is not enforced at runtime.

>lua
  local result = require("cds.result")
  local value, err = result.map(false, nil, tostring)
  assert(value == "false" and err == nil)
<

------------------------------------------------------------------------------
                                                          *cds.result.context()*
                   `result.context`({value}, {err}, {prefix})
Add the location or operation that makes an error actionable. A parser may
know what went wrong but not which setting it was parsing; its caller can
add that information without changing the successful value. On failure,
`err` must be a string; include any separator in `prefix`.

>lua
  local result = require("cds.result")
  local value, err = result.context(nil, "expected a number", "retries: ")

  assert(result.context(3, nil, "retries: ") == 3)

------------------------------------------------------------------------------
                                                         *cds.result.traverse()*
                       `result.traverse`({values}, {fn})
Build a list only if every item can be transformed successfully. Call
`fn(value, index)` in order and stop at the first nil result, returning
`nil, err` instead of a partial list. An empty input succeeds with `{}`.
Earlier callback effects are not undone; use pure callbacks when a failed
batch must leave nothing changed.

>lua
  local result = require("cds.result")
  local function number(text, i)
    local n = tonumber(text)
    if n == nil then return nil, "item " .. i .. ": expected a number" end
    return n
  end
  local values = assert(result.traverse({ "10", "20" }, number))
  assert(values[1] == 10 and values[2] == 20)
  local value, err = result.traverse({ "10", "bad", "30" }, number)
  assert(value == nil and err == "item 2: expected a number")
<

{values} `(T[])`
{fn} `(fun(value: T, index: integer): U?, any)`
Return ~
`(U[]?)` values

                                                                    *cds.module*
Give callers a useful error when they call an API that is missing from an
installed library. `wrap` makes the error identify both the module and the
requested name, helping distinguish a typo from an outdated dependency.
Every module in cds-lua-fp except this one uses it.

Wrap a module when returning its public table: >lua

  local module = require("cds.module")
  local api = module.wrap("example", { greet = function() return "hello" end })
  assert(api.greet() == "hello")
  local ok, err = pcall(function() api.greet_missing() end)
  assert(not ok and err:find('cds.example has no "greet_missing"', 1, true))
<
A missing lookup returns a fallback function; the error occurs when that
function is called. Consequently, `if api.some_name then` cannot test
whether an API exists. Use |cds.module.is_fallback()| or |cds.needs.check()|
for that purpose. `wrap` replaces the table's metatable, so use it on plain
module tables, not tables whose existing metamethods must be preserved.

------------------------------------------------------------------------------
                                                             *cds.module.wrap()*
                          `module.wrap`({name}, {mod})
Attach missing-API diagnostics to a module table and return the same table.
Existing fields keep their values. `name` is the suffix after `cds.`, such
as `fp` or `html.blocks`, and is used in the error message.

>lua
  local module = require("cds.module")
  local api = { version = 1 }
  assert(module.wrap("example", api) == api)
  assert(api.version == 1)
<
Parameters ~
{name} `(string)` "fp", "html.blocks"
{mod} `(T)`
Return ~
`(T)`

------------------------------------------------------------------------------
                                                      *cds.module.is_fallback()*
                         `module.is_fallback`({value})
Identify a function created by `wrap` for a missing field. Use this after a

                                                                     *cds.needs*
Check required library APIs before a plugin starts, so an outdated
installation produces one actionable message instead of failing later in
an unrelated command. Declare the names the plugin uses, then run `check`
at its entry point. This checks availability, not function signatures or
behavior, so it complements version constraints and tests.

For example, check the requirements of a plugin that transforms lists: >lua

  local needs = require("cds.needs")
  local capabilities = { fp = { "map", "filter" }, result = { "bind" } }
  local problem = needs.check("example.nvim", capabilities)
  assert(problem == nil) -- these APIs are available in this library

  problem = needs.check("example.nvim", { fp = { "not_an_api" } })
  assert(problem:find("fp.not_an_api", 1, true))
  assert(problem:find("cds-io/cds-lua-fp", 1, true))
<
In a plugin entry point, report a non-nil problem and return before
registering commands or autocommands. Load `cds.needs` with `pcall(require,
"cds.needs")` there too: an installation too old to include this module
cannot check its own capabilities.

Keep the declaration in one module, such as `lua/example/needs.lua`, and
use the same table with |cds.needs.strict()| in the test harness. This catches
new library calls that were added without updating the startup check.
Declare table-valued APIs, such as `http.status`, by their top-level name.

Install cds-lua-fp directly for the pure Lua helpers. A Neovim plugin using
APIs from cds-lua should declare that library as a dependency; it brings
cds-lua-fp with it. Missing-API messages name the library to install or
update: cds-lua-fp for `fp`, `result`, `module`, and `needs`; cds-lua for the
remaining modules.

------------------------------------------------------------------------------
                                                             *cds.needs.check()*
                    `needs.check`({plugin}, {capabilities})
Return nil when all declared APIs are available. Otherwise, return one
message naming the plugin, the missing APIs, and the libraries to install
or update. The caller owns how that message is displayed; this function
does not notify, throw, or disable the plugin itself.

>lua
  local needs = require("cds.needs")
  assert(needs.check("example.nvim", { fp = { "map" } }) == nil)
  local problem = needs.check("example.nvim", { fp = { "not_an_api" } })
  assert(problem == "example.nvim needs cds-lua-fp with fp.not_an_api: "
    .. "install or update cds-io/cds-lua-fp")
<

{plugin} `(string)` truth-table.nvim
{capabilities} `(cds.needs.Capabilities)`
Return ~
`(string|nil)`

------------------------------------------------------------------------------
                                                            *cds.needs.strict()*
                    `needs.strict`({plugin}, {capabilities})
Catch undeclared library usage during tests. Before loading plugin modules,
call this with the same capabilities used by the startup check. It replaces
declared modules in `package.loaded` with proxies that reject reads of
undeclared names. Modules absent from the declaration are not intercepted.

Writes pass through to the original module, allowing tests to replace hooks.
Calls originating inside `lua/cds/` are exempt, since the library's own
implementation may need additional APIs. Modules that cannot load are
skipped. Run this in a test process, not in normal plugin startup: the
proxies persist for the lifetime of that process.

>lua
  local needs = require("cds.needs")
  local capabilities = { fp = { "map" } }
  needs.strict("example.nvim", capabilities)
  local fp = require("cds.fp") -- require after installing the proxies
  assert(fp.map({ 2 }, function(n) return n * 2 end)[1] == 4)
  local ok, err = pcall(function() return fp.filter end)
  assert(not ok and err:find("without declaring it", 1, true))
<
Parameters ~
{plugin} `(string)`
{capabilities} `(cds.needs.Capabilities)`
